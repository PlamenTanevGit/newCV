# AI-Assisted QA Workflows

**Evidence level: practical working method, partly documented in Drive and GitHub.** This is productivity use of AI assistants in QA. It is not AI engineering, and no results or time savings are claimed.

## Project Overview

I use AI assistants (GitHub Copilot, ChatGPT, Claude, Gemini, NotebookLM) to speed up routine QA tasks, with human review of every output. Evidence you can inspect:

## Problem / Context

QA has a lot of writing and reading: test cases, bug reports, documentation, unfamiliar code. AI can draft and summarise quickly, but it can also invent details. The workflow needs guard-rails so that speed does not cost accuracy.

## Tools Used

GitHub Copilot, ChatGPT, Claude, Gemini, NotebookLM, VS Code, Markdown files for reusable context.

## QA Approach

1. **Give context, not just a question:** a Markdown file with product notes, terminology, test-case format and what *not* to assume.
2. **Ask for drafts in my team's format:** test cases, boundary lists, negative cases, exploratory charters.
3. **Review everything:** check each case against the requirement, remove invented behaviour, add missing risks.
4. **Never paste confidential data** (customer data, secrets, internal code) into public tools. Use sanitised examples.
5. **Keep the human decisions:** priorities, risk calls, sign-off.

## What Was Tested

The method is applied to: drafting test cases from user stories, generating boundary and negative variants, summarising long defect threads, explaining unfamiliar test frameworks, and drafting documentation.

## Example Scenarios

1. Paste a user story and acceptance criteria into an assistant with a team template → get draft test cases → review and edit.
2. Give a large, unfamiliar framework folder structure to an assistant → get an explanation of layers → verify by reading the code.
3. Ask for ten boundary and negative cases for a form field → keep the meaningful ones.

## Example Test Cases

Example prompt (generic, no confidential data):

```text
Role: senior QA engineer. Format: ID, title, preconditions, steps, expected result, priority, type.
Context: web form "New work request" with fields: location (required), category (required),
description (required, max 500 chars), priority (High/Medium/Low), attachment (jpg/png/pdf, max 5 MB).
Task: propose 12 test cases: 4 positive, 4 negative, 4 boundary.
Rules: do not invent fields or behaviour not listed. Mark any assumption with "ASSUMPTION:".
```

Human review checklist for the output:
- [ ] Every case maps to a listed field or rule.
- [ ] No invented behaviour (check all "ASSUMPTION:" lines).
- [ ] Boundaries are exact (500 and 501 characters, 5 MB and just over).
- [ ] Priorities adjusted to real risk.

## Business Value

No measured savings are claimed. The aim is to spend less time on first drafts and more on risk, exploration and review.
