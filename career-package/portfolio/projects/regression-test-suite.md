# Regression Test Suite

**Evidence level: public framework structure plus CV statements.** Employer regression suites are confidential and are not shown. No metrics are claimed on this page.

## Project Overview

How I build and maintain regression coverage: a small, stable smoke layer, critical-flow tests, and wider checks that run on a schedule. Publicly visible evidence:

- The Selenium/TestNG framework in https://github.com/PlamenTanevGit/LamdaTestRefact uses a `testng.xml` suite with parallel execution and reporting, which is the structure of a regression suite (suite file, listeners, reports).
- A Playwright workflow in https://github.com/PlamenTanevGit/Claude_Sinoptik_Autogenerated that runs on push and pull request.
- TestNG regression suite files from 2018–2021 exist in my Google Drive (for example `testng_regression.xml`, `Regression1.xml`). Their content was not opened for this portfolio and they may be training material.
- A reusable manual [regression checklist](../samples/sample-regression-checklist.md).
- CV statements about regression at Nuvolo (reduced manual effort, faster releases). Those numbers are unverified and are on the CV only.

## Problem / Context

Every release risks breaking something that worked. Manual regression alone becomes slow as the product grows, while automation alone misses new and unusual behaviour. The aim is a balance: automate stable, high-value flows and keep human time for exploration and new features.

## Tools Used

Selenium (Java, TestNG), Playwright (JavaScript), Postman, Jira, TestRail or Zephyr for manual suites, Jenkins and GitHub Actions for scheduled runs.

## QA Approach

1. **Smoke** (minutes): can the application start, log in and open the main pages? Failure stops the run and raises an alert.
2. **Critical flows:** the journeys that earn money or protect data (create, edit, approve, search, permissions).
3. **Data and API checks:** response codes, saved values, no duplicates.
4. **Cross-browser:** run the critical flows on the supported browsers.
5. **Selection by risk:** each release, add extra checks for changed areas using the risk analysis ([sample](../samples/sample-qa-risk-analysis.md)).
6. **Maintenance:** remove flaky tests or fix their cause, review selectors, retire tests for removed features.

## What Was Tested

Illustrative checklist areas: login and session, create and edit records, search and filter, permissions, notifications, exports, negative scenarios.

## Example Scenarios

1. After a release candidate is built, the smoke set runs automatically and blocks the full run on failure.
2. A changed permissions module triggers an extended role × action check.
3. A flaky test fails twice in a week and is investigated: wait strategy, data dependency or a real defect.

## Example Test Cases

| ID | Title | Layer | Expected |
|---|---|---|---|
| REG-01 | Application loads and login works | Smoke | Home page shown after valid login |
| REG-02 | Create and view a record | Critical flow | Saved data visible in list and detail, no duplicates |
| REG-03 | Role cannot access a restricted page | Permissions | Access denied (UI and direct URL) |
| REG-04 | Critical flow on the second browser | Cross-browser | Same result as on the primary browser |

## Business Value

No metrics are claimed on this page. The intended value is faster, calmer releases: problems found earlier, a clear go/no-go report, and less repeated manual effort.

## What I Would Improve Next

- Tag tests (`smoke`, `regression`) and run the right set per trigger (pull request, nightly, release).
- Add a flakiness report (failure history per test) and a rule for quarantining tests.
- Track coverage by requirement, not by test count.
- Publish a small demo suite with CI and a report as a portfolio piece.
