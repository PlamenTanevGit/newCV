# Playwright Test Suite: Weather Site and Demo Form

**Evidence level: real public repository.** Findings below come from reading the repository on 2026-10-01.

## Project Overview

A JavaScript Playwright suite that tests navigation and page content on a public Bulgarian weather site (sinoptik.bg) and the validation of a public demo-request form (payhawk.com). The repo name suggests the tests were generated with AI assistance and then adjusted by hand; the repo has no README, so that is an inference from the name only.

## Problem / Context

Practice project to build a modern Playwright setup end to end: tests, reporters, failure artefacts and a GitHub Actions run. Weather pages combine dynamic content (forecast tables, location lists), a consent pop-up and mobile layouts, which makes them a useful, realistic target for UI test design.

## Tools Used

- Playwright Test (`@playwright/test` ^1.40), JavaScript, Node 18+ (Node 20 in CI)
- Reporters: list, HTML and JUnit XML
- Traces, screenshots and video retained on failure
- ESLint and Prettier
- GitHub Actions

## QA Approach

- Specs are grouped by area (`bulgaria_locations`, `europe_locations`, `sinoptik_test`, `payhawk_test_spec`) with `test.describe` and `test.step` for readable reports.
- A shared helper handles the cookie-consent pop-up (`tests/utils/consent-handler.js`).
- `beforeEach`/`afterEach` hooks manage navigation and capture a screenshot on failure.
- Mobile checks use an explicit viewport (375 × 667).
- CI retries failed tests twice and uses two workers; failure artefacts are uploaded from the workflow.

## What Was Tested

- Location links in regional sections (for example Western Europe) and navigation to a country page.
- 14-day and 5-day forecast navigation tabs and the structure of the forecast data.
- Presence and behaviour of key links on a mobile viewport.
- Demo-request form validation: empty form, valid input, email format.

## Example Scenarios

1. A user opens the 14-day forecast and the forecast table structure is correct (days, temperatures).
2. A user on a 375 × 667 phone viewport still sees the Bulgaria link and can follow it.
3. A user clicks the Italy link in the Europe section and lands on the Italy forecast page.
4. A visitor submits the demo form with an invalid email and sees a validation message.

## Business Value

This is a practice project, not production work, so no business results are claimed. It shows how I structure UI tests for dynamic public pages, how I collect evidence on failure (trace, video, screenshot), and how I connect tests to CI.

## What I Would Improve Next

Honest list based on what I found in the repo:

- Add a README (purpose, how to run, how CI works).
- Remove committed `node_modules/`, report folders, `results.xml` and failure screenshots; add them to `.gitignore`.
- Tighten weak assertions (for example a count check that accepts 0) and re-enable commented-out assertions.
- Run **all** specs in CI (the workflow currently runs two of them) and enable Firefox and WebKit projects.
- Introduce page objects or fixtures and prefer role/test-id locators over XPath where possible.
- Confirm the demo-form tests never submit a real request to a third-party company. Keep checks read-only and respect each site's terms.
- Pin a Playwright version policy and add a scheduled nightly CI run.
